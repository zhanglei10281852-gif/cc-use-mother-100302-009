# 传动设备本地化设计闭环

面向从"来图生产"转向"面向中国客户自主研发"的动力传动设备厂商，本项目提供一组纯 Python 领域契约与闭环服务，覆盖：

> 客户现场问题（带来源）→ 需求 → 澄清 / 冲突分析 / 优先级确认 → 产品配置与设计基线 → 计算校核 / 样机验证 / 供应商替代 / 工程变更 → 交付序列号 → 变更传播 → 双向追踪

不依赖浏览器、外部数据库或其他运行服务；服务层当前为内存态仓储，便于后续替换为持久化实现而不改变领域规则。

## 核心业务规则

- **带来源的需求**：每条需求必须引用已登记的客户声音（现场报告、会议纪要、客户邮件、法规条款等）。销售口头承诺无来源不得进入设计基线。
- **需求门禁**：需求须经过澄清（环境/载荷/维护边界）和优先级确认，才能进入配置基线；已撤回/被替代需求不得入基线。
- **发布门禁**：
  - 未解决的**安全冲突不得发布**，且安全冲突不允许以偏差放行，必须由设计决定解决；
  - 接受**偏差必须说明适用客户与到期日**，偏差适用客户须覆盖受冲突影响需求的全部适用客户，偏差到期后新版本不得发布；
  - 发布时固化基线指纹与需求依据指纹。
- **交付原依据**：序列号交付时固化配置版本、需求清单与基线指纹；后续变更不回改已交付依据，只产生通知/服务公告。
- **变更传播**：需求撤回、法规更新、零件停产、供应商替代、验证失败通过工程变更单传播到受影响配置，配置视图中呈现待消化变更与开放风险；验证失败自动生成返工变更。
- **法规更新**：以新需求接替旧需求（`supersedes`），旧需求标记 `superseded`，可进入配置新版本重新走发布门禁。
- **可查询**：任一配置可查询有效需求、验证覆盖（含未覆盖的安全需求）、开放风险（未解决安全冲突、在用/到期偏差、失败验证、待消化变更）与已交付序列号。
- **双向追踪**：客户声音 → 需求 → 设计决定（含计算书）→ 验证 → 配置基线 → 交付序列号正向可追踪；由需求或设计决定可反向追溯到来源凭证。

## 代码结构

- `src/local_design/contracts.py`：不可变对象、版本演进（`evolve`）、稳定指纹、必填/日期校验。
- `src/local_design/models.py`：`Source` / `VoiceOfCustomer` / `Requirement` / `Conflict` / `DesignDecision` / `VerificationRecord` / `ProductConfiguration` / `DeliveredUnit` / `EngineeringChange` 及状态枚举。
- `src/local_design/service.py`：`LocalDesignLoop` 闭环服务（状态推进、发布门禁、传播、查询视图、双向追踪、审计日志）。
- `tests/`：基础契约测试与以矿山/风电/机器人产线为背景的闭环规则测试。

## 运行环境

- Python 3.11 或更高版本
- Linux、macOS 或 Windows

## 运行测试

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

## 编译检查

```bash
python3 -m compileall -q src tests run_cli.py
```

## 命令行冒烟

```bash
python3 run_cli.py
```

命令会演示一条端到端链路：矿山现场报告转需求 → 安全冲突由设计决定解决 → 样机验证通过 → 配置发布与序列号交付 → 现场验证失败自动传播（序列号保持原依据）→ 双向追踪结果与审计日志。
